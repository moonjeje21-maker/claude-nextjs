# 코드 리뷰 서브에이전트 만들기 계획

- 날짜: 2026-10-05
- 프로젝트: claude-nextjs (브랜치 `main`, 커밋되지 않은 변경 없음)
- 상태: 완료 (2026-10-05, 커밋 전). 테스트에서 찾은 문제 1건을 고쳐 다시 확인했다 — 맨 아래 "테스트 결과"와 "고친 내용" 참고

## Context (왜 하는가)

**서브에이전트**는 Claude Code가 일을 맡길 수 있는 "별도의 작은 Claude"다. 자기만의 대화 공간에서 일하고 결과만 돌려주므로, 코드를 쓴 대화의 생각에 끌려가지 않고 코드를 새로 읽는다.

`.claude/agents/`에 md 파일 하나를 두면 서브에이전트가 된다 (지금 이 폴더는 없다). 여기에 **코드가 올라가기 전 마지막으로 보는 CTO 역할**의 리뷰 에이전트를 만든다.

- 읽기 전용: 도구는 `Read`(파일 읽기), `Grep`(내용 검색), `Glob`(파일 이름 검색) 셋뿐
- 모델: Fable 5.1

## 2차 검토 결과 (CTO 최종 리뷰어로 맞게 동작하는가)

에이전트가 일하는 순서대로 첫 초안을 따져 보았다.

| 단계 | 첫 초안의 문제 | 고친 내용 |
|---|---|---|
| 1. 역할 | "문제를 찾아 보고한다"뿐이라 평범한 검사기였다. 최종 검토자가 내려야 할 **결정**이 없었다 | 첫 문단에 역할과 판단 하나를 적었다: "이대로 올려도 되는가" |
| 2. 입력 | 변경 의도가 없을 때 어떻게 할지 없었다. 의도를 모르면 "의도대로 동작하는가"를 판단할 수 없다 | 의도가 없으면 코드에서 읽어 낸 의도를 밝히고 그 기준으로 검토한다 |
| 3. 판단 기준 | 버그 종류를 나열한 목록이었다. 무엇이 올리기를 막는 문제이고 무엇이 아닌지 구분이 없었다 | 기준 4개(동작 → 위험 → 구조·규칙 → 유지보수)로 바꾸고, 앞의 둘은 올리기 전에 반드시 고칠 문제로 정했다 |
| 4. 보고 | 문제 목록만 있고 승인 여부가 없었다 | 결론을 승인 / 수정 후 승인 / 반려 중 하나로 내고, "지금 고칠 것"과 "나중에 고쳐도 되는 것"을 나눴다 |
| 5. 한계 | lint·build를 못 돌리는데도 그냥 승인할 수 있었다 | 결과를 받지 못했으면 lint·build 통과를 **승인 조건**으로 적게 했다 |

지운 내용 (본문 약 45줄 → 약 25줄):

## 만들 파일 (1개): `.claude/agents/code-reviewer.md`

맨 위 `---` 사이가 **frontmatter**(파일의 설정값을 적는 머리말)이고, 그 아래가 에이전트에게 주는 지시문이다.

| 설정 | 뜻 |
|---|---|
| `name` | 부를 때 쓰는 이름 |
| `description` | Claude가 "언제 이 에이전트에게 맡길지" 판단할 때 읽는 설명 |
| `tools` | 이 셋만 쓸 수 있다. 파일 수정(`Edit`·`Write`)과 명령 실행(`Bash`)이 빠져 있어 아무것도 바꾸지 못한다 |
| `model` | `claude-fable-5-1`은 Fable 5.1의 정식 모델 ID다. 짧은 이름 `fable`은 "가장 최신 Fable"이라 새 버전이 나오면 따라 바뀌므로, 5.1로 고정하려고 정식 ID를 쓴다 |

전체 내용:

````markdown
---
name: code-reviewer
description: CTO 관점의 최종 코드 리뷰. 코드 변경을 커밋이나 PR로 올리기 전에 읽기 전용으로 검토해서 승인 여부와 고쳐야 할 문제를 보고한다. git을 실행하지 못하므로 부를 때 리뷰할 파일 경로와 변경 의도를 넘긴다 (diff, lint·build 결과가 있으면 함께).
tools: Read, Grep, Glob
model: claude-fable-5-1
---

이 저장소의 CTO로서, 코드 변경이 `main`에 들어가기 전에 마지막으로 검토한다. 이 뒤에 더 보는 사람이 없으므로 내릴 판단은 하나다: 이 변경을 이대로 올려도 되는가. 파일을 읽고 찾는 도구만 있어서 코드를 고치지 않는다. 판단과 근거를 보고하고, 고치는 일은 보고를 받은 쪽이 한다.

## 리뷰 대상

요청에 적힌 파일 경로와 diff가 리뷰 대상이다. 대상이 적혀 있지 않으면 저장소 전체를 짐작으로 훑지 말고, 어떤 파일을 봐야 하는지 묻고 끝낸다. 변경 의도가 적혀 있지 않으면 코드에서 읽어 낸 의도를 보고 첫머리에 밝히고 그 기준으로 검토한다.

대상 파일은 바뀐 줄만이 아니라 전체를 읽는다. 바뀐 함수, 컴포넌트, 타입을 쓰는 곳도 Grep으로 찾아서 이 변경 때문에 다른 파일이 깨지지 않는지 확인한다.

## 판단 기준

중요한 순서대로 본다.

1. 의도한 대로 동작하는가: 변경 의도와 실제 코드가 맞는지, 잘못 동작하는 입력이나 상태가 있는지
2. 올리면 위험한가: 보안 문제, 기존 화면이나 기능을 깨뜨리는 변경
3. 구조와 규칙에 맞는가: 기준은 `CLAUDE.md`와 `.claude/rules/`다
4. 앞으로 유지하기 쉬운가: 이미 있는 코드를 두고 새로 만든 중복, 필요 이상으로 복잡한 구조, 의도와 상관없이 섞여 들어온 변경

1과 2에 걸리는 문제는 올리기 전에 고쳐야 한다. 3과 4는 영향이 큰 것만 올리기 전에 고칠 문제로 올리고, 나머지는 나중에 고쳐도 되는 것으로 나눈다. 취향 차이는 보고하지 않는다.

Next.js API 사용이 틀렸다고 지적하기 전에 `node_modules/next/dist/docs/`에서 해당 문서를 확인한다.

## 보고

한국어로, 아래 순서로 쓴다. 문제가 없으면 없다고 쓰고, 보고할 거리를 채우려고 사소한 것을 끌어오지 않는다.

1. 결론: 승인 / 수정 후 승인 / 반려(접근 자체를 다시 잡아야 할 때) 가운데 하나와 그 이유 한 문장
2. 올리기 전에 고쳐야 할 문제: 심각한 순서로. 문제마다 `파일경로:줄번호`, 무엇이 문제인지, 어떤 상황에서 어떻게 잘못되는지, 고치는 방향을 적는다. 코드를 직접 읽어 확인한 것만 단정하고, 실행해 봐야 알 수 있는 것은 "추정"이라고 표시한다
3. 나중에 고쳐도 되는 것: 한 줄씩
4. 승인 조건: lint와 build를 직접 돌릴 수 없다. 요청에 결과가 없으면 `npm run lint`와 `npm run build` 통과를 조건으로 적는다
````

### 알아 둘 점: 읽기 전용의 대가

`Bash`가 없어서 이 에이전트는 `git diff`(무엇이 바뀌었는지 보는 명령)도 lint·build도 직접 돌리지 못한다. 그래서 부르는 쪽(이 대화의 Claude)이 파일 경로와 변경 의도를 넘겨야 하고, 이 점을 `description`에 적어 두었다. 대신 실수로라도 파일을 바꾸거나 명령을 실행할 일이 없다.

## 고치지 않는 것

- `CLAUDE.md`, `README.md`, `.claude/rules/`: 서브에이전트는 `.claude/agents/`에 있으면 자동으로 발견되므로 따로 안내를 적지 않는다
- 커밋·푸시는 하지 않는다. 따로 요청받으면 올릴 내용을 먼저 보여 주고 확인받은 뒤 브랜치(`chore/…`) → PR 방식으로 한다. `.claude/agents/`는 git이 무시하지 않으므로 커밋하면 저장소에 함께 올라간다

### 테스트 결과 (2026-10-05)

만든 대화에서는 `code-reviewer`가 보이지 않았다("Agent type 'code-reviewer' not found"). 서브에이전트 목록은 대화를 시작할 때 읽히기 때문이다. `/agents` 명령은 없어져서 쓸 수 없었다. 그래서 `claude -p`(화면 없이 새 Claude Code를 한 번 실행하는 방법)로 새 실행을 두 번 띄워 확인했다.

| 확인 | 결과 |
|---|---|
| 새 실행이 에이전트를 발견하는가 | 통과. 에이전트 목록에 `code-reviewer`가 있다 |
| 모델과 도구 | 통과. 에이전트의 모든 응답이 `claude-fable-5-1`이었고, 쓴 도구는 `Read`·`Grep`·`Glob`뿐이다. 테스트 뒤 `git status`에 바뀐 파일 없음 |

### 고친 내용 (2026-10-05)

위 실패를 (가) "항상 되묻기"로 고쳤다. `code-reviewer.md`의 "리뷰 대상" 첫 문단을 아래처럼 바꿨다. 그래서 이 파일은 위 "만들 파일"의 초안과 이 문단만 다르다.

> 요청에 적힌 파일 경로와 diff가 리뷰 대상이다. 대상이 적혀 있지 않으면 어떤 파일을 봐야 하는지 묻고 끝낸다. 시작할 때 받는 git 상태 요약에 바뀐 파일이 보여도 그것을 대상으로 삼지 않는다. 요약은 대화를 시작한 시점의 기록이라 지금 상태와 다를 수 있고 어느 줄이 바뀌었는지도 담겨 있지 않아서, 엉뚱한 파일을 보고 승인할 수 있기 때문이다. 저장소 전체를 짐작으로 훑지도 않는다.

다시 확인: 같은 요청("방금 한 변경을 리뷰해 줘", 경로 없음)을 새 실행으로 넘겼다. 에이전트는 도구를 하나도 쓰지 않고, 대상이 없어 검토를 시작하지 않았다며 파일 경로를 되물었다. 통과.

### 남은 작업

- 커밋하지 않았다. 새 파일: `.claude/agents/code-reviewer.md`, 이 계획 파일. 커밋·푸시는 따로 요청받았을 때만, 올릴 내용을 먼저 보여 주고 확인받은 뒤에 한다 (브랜치 `chore/…` → PR 방식)
- 이 에이전트는 새 대화부터 쓸 수 있다 (만든 대화에서는 목록에 보이지 않는다)
